Spec-Driven Development with Claude Code

Home Blog Spec-Driven Development

September 2026 · Abdelrahman Khalawy

Claude Code is a core part of how I build software — across SehhaTech and the Student Management Platform, and everything in between. But the workflow that matters isn't "ask AI to generate code." It's closer to how I'd hand off work to a capable engineer who just joined the team: give them the spec, the constraints, and the reasoning behind past decisions — then review what they produce before it ships.

Why prompts alone don't scale

Early on, working with an AI assistant can feel like describing what you want in a sentence and getting code back. That works for small, isolated tasks. It stops working the moment a change has to respect rules that live outside the file being edited — a tenancy boundary, a naming convention, a decision someone made three weeks ago for a reason that isn't obvious from the code alone.

On a multi-tenant system like SehhaTech, that gap is dangerous. A change that looks locally correct can quietly break tenant isolation if the person (or model) making it doesn't know the rule exists. So the fix isn't a cleverer prompt — it's giving Claude Code the same context a human teammate would need.

What "specification-driven" looks like

In practice, this means Claude Code works against a small set of durable references instead of a one-off instruction:

  • Written specifications — what a feature or endpoint is supposed to do, including edge cases, before any implementation starts.
  • Architectural rules — the layering a backend has to respect (for example, a controller should never reach the database or an infrastructure service directly), and the tenancy boundaries that must hold no matter what.
  • Decision logs — short records of why a past decision was made, so a change six weeks later doesn't silently reverse it.
  • Project context — the domain language and conventions already in use, so new code reads like it belongs.

With that in place, I can point Claude Code at a real task — "add a reception dashboard endpoint that respects the existing tenant scoping" — and it has enough grounding to produce something worth reviewing, instead of something that merely compiles.

A draft, not a decision

The part of this workflow I'd push back on hardest is treating AI output as finished. It isn't. Every change — backend code, a database migration, a test, a piece of documentation — goes through the same review it would if a teammate had written it: does it actually satisfy the spec, does it respect the architecture, does it introduce anything that weakens tenant isolation, and are the tests meaningful rather than decorative.

On SehhaTech, that review is backed by something stronger than good intentions: architecture tests that fail the build if an entity is introduced without the tenant isolation rules being wired up correctly. That's the real safety net — not trusting either a human or an AI to remember the rule every time, but making the rule impossible to silently skip.

Where this workflow actually helps

This approach shows up across the whole lifecycle, not just implementation:

  • Requirements decomposition — turning a vague feature request into a spec with explicit edge cases.
  • Architecture review — using Claude as a thinking partner to pressure-test a design before writing any code.
  • Refactoring — with the architectural rules as a constraint, so a refactor can't quietly drift outside the intended structure.
  • Technical documentation — keeping specs and decision logs current is itself a task Claude Code helps with, as long as a human is still the one who confirms what's actually true.

Teaching this to other developers

I've shared this workflow with engineering teammates and CS classmates — how to structure a prompt so it carries real context instead of just an instruction, how to manage that context as a project grows, and how to use Claude as a review partner rather than only a code generator. The single biggest shift I've seen when someone adopts this: they stop asking "did the AI get this right?" and start asking "does this match the spec I gave it?" — a much easier question to answer, and a much safer one to be wrong about.
