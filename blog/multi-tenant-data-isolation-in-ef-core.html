Multi-Tenant Data Isolation in EF Core

Home Blog Multi-Tenant Data Isolation

September 2026 · Abdelrahman Khalawy

SehhaTech is a multi-tenant healthcare management SaaS — every clinic that subscribes gets what looks, from the inside, like its own private system. Patients, doctors, schedules, appointments, and analytics for one clinic must never be visible to another. On a shared database, that guarantee can't rest on "the developer remembered to filter by clinic." It has to be enforced at the infrastructure level, the same way for every query, whether a human or an AI wrote it.

The problem with per-query filtering

The naive approach to multi-tenancy is: every query includes a WHERE ClinicId = @currentClinicId. It works — until it doesn't. Someone adds a new query, a new report, a new admin tool, and forgets the filter once. On a single-tenant system that's a bug. On a multi-tenant system, it's a data breach: one clinic's patient records rendered on another clinic's screen.

The fix isn't discipline. It's removing the chance to forget.

Per-request access scoping

Every request into SehhaTech resolves the current tenant once, early, through middleware — before it ever reaches a controller or a query. That resolved tenant context is then available for the lifetime of the request, so nothing downstream has to re-derive "who is asking" or trust a value passed in from the client.

Named global query filters

Instead of scattering Where(x => x.ClinicId == tenantId) across every query, tenant-scoped entities carry a named global query filter configured once in the DbContext. EF Core applies it automatically to every query against that entity — reads, includes, projections — without each call site having to opt in. A query that forgets to think about tenancy still gets the correct, isolated result, because isolation isn't something a query author decides case by case. It's a property of the entity itself.

Naming the filter also matters more than it sounds: it makes the rule discoverable and testable in isolation, instead of being an anonymous lambda buried in configuration that nobody remembers adding.

Architecture tests: making the rule impossible to skip

Global query filters only help if every tenant-scoped entity actually has one. So SehhaTech has automated architecture tests that check exactly that — if a new entity is added that should be tenant-scoped but isn't wired into the isolation setup, the build fails. Not a code review comment, not a linter warning: a red build.

This is the same principle from spec-driven development applied to safety-critical rules: don't rely on the rule being remembered — make violating it impossible to merge. That matters as much for AI-assisted changes as it does for anything a human writes. Claude Code can propose a new entity or a new query; the architecture tests are what actually enforce that it respects tenancy, regardless of who — or what — wrote it.

Clean layering underneath it

None of this works if a controller can reach the database directly and route around the rules. SehhaTech's backend follows a strict, one-directional layering — domain, core, application, infrastructure, then the API hosts — so the only path to the database is through the layer where tenant isolation is enforced. Two independent API hosts (the clinic system and the patient portal) share everything below that boundary and the same SQL Server database, with isolation guaranteed at the query-filter level rather than trusted to each host individually.

Why this is worth writing down

Multi-tenant isolation is the kind of thing that's invisible when it works and catastrophic when it doesn't. Designing it as infrastructure — scoped once per request, enforced by named filters, guarded by a failing build — means the guarantee doesn't depend on anyone's memory. That's the bar I hold any multi-tenant system I build to, including the unified identity model behind the Student Management Platform, which I'll get into in the next post.
